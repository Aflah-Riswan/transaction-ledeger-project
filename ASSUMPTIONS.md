# Assumptions and Design Decisions

## 1. Account Management

- **Unique Identification**: Each account is assigned a unique identifier (24-character hexadecimal MongoDB `ObjectId`) generated by the database upon creation.
- **Account Name**: An account must have a non-empty name (trimmed of leading and trailing whitespace).
- **Initial Balance**: Every new account starts with an initial balance of strictly `0`. Clients cannot initialize an account with an arbitrary balance.
- **Server-Controlled Timestamps**: Creation and update timestamps (`createdAt`, `updatedAt`) are managed solely by the server and database, not the client.
- **Account Verification**: An account must exist before any transaction can be processed against it.

---

## 2. Money Representation

- **Integer Minor Units**: Transaction amounts and account balances are represented as positive whole integers in minor currency units (e.g., cents or paise). This completely eliminates floating-point rounding errors and precision issues.
- **Strict Positive Amounts**: Credit and debit amounts must be integers strictly greater than zero (`> 0`). Negative amounts and zero values are rejected.
- **No Floating Points or Leading Zeros**: Decimals and numbers with leading zeros (e.g., `099`) are rejected by both frontend and backend validators.
- **Direct Balance Modification Prohibited**: Clients cannot directly set or alter an account balance. The balance can only be mutated through valid credit or debit ledger entries.

---

## 3. Transaction References and Idempotency

- **Reference ID Required**: Every transaction request must supply a non-empty string `referenceId` (e.g., from an upstream payment gateway or client-generated idempotency key).
- **Account-Scoped Uniqueness**: A `referenceId` must be unique within the context of a single account. The same `referenceId` may be reused across different accounts.
- **Duplicate Request Handling**: Duplicate transaction references submitted to the same account are rejected with an HTTP `409 Conflict` without modifying the balance or creating duplicate entries.
- **Database-Level Constraint**: Idempotency is enforced at the database level via a compound unique index on `{ accountId: 1, referenceId: 1 }`, guaranteeing safety against concurrent duplicate submissions.

---

## 4. Credit and Debit Operations

- **Credit**: A credit transaction increases the account balance by the transaction amount.
- **Debit**: A debit transaction decreases the account balance by the transaction amount.
- **Overdraft Protection**: A debit request is rejected with HTTP `400 Bad Request` if the account has insufficient funds. Balances are never permitted to drop below zero.
- **Atomic State Updates**: Account balance deduction is executed atomically using conditional operators (`balance >= amount`). If a transaction ledger insert fails, a compensating rollback restores the balance.

---

## 5. Ledger Immutability

- **Append-Only Ledger**: Transactions function as immutable financial records.
- **No Direct Modification or Deletion**: The API does not expose any `PUT`, `PATCH`, or `DELETE` endpoints for transactions.
- **Historical Integrity**: The transaction `type`, `amount`, `description`, `referenceId`, `accountId`, and `createdAt` timestamp cannot be altered once recorded.
- **Reversals**: Reversals or corrections in a ledger model are represented by new, compensating transactions rather than editing existing records.

---

## 6. Transaction History and Pagination

- **Ordering**: Transaction records are returned in reverse chronological order (newest first) based on `createdAt: -1`, with a secondary sort on `_id: -1` for stable ordering when timestamps match.
- **Type Filtering**: Transaction history supports optional filtering by transaction type (`credit` or `debit`). Omitting the filter returns all transactions.
- **Pagination Controls**: Query parameters `page` and `limit` allow paginated browsing:
  - Default `page`: `1`
  - Default `limit`: `10`
  - Maximum `limit`: `100` (requests exceeding 100 are capped)
- **Pagination Metadata**: Every history response includes metadata: `page`, `limit`, `totalRecords`, and `totalPages`.

---

## 7. Validation and Error Handling

- **Explicit Validation**: Input payloads are strictly validated before reaching the domain layer. Invalid types, missing fields, or negative values return HTTP `400 Bad Request`.
- **Malformed vs. Non-Existent IDs**:
  - Malformed account IDs (not a valid 24-character hexadecimal format) return HTTP `400 Bad Request`.
  - Well-formed IDs that do not exist in the database return HTTP `404 Not Found`.
- **Conflict Handling**: Duplicate reference IDs return HTTP `409 Conflict`.
- **Consistent Response Envelope**: All API responses follow a uniform JSON structure:
  - Success: `{ "success": true, "data": ... }`
  - Error: `{ "success": false, "message": "Detailed error message" }`
- **Internal Protection**: Unhandled exceptions return a generic HTTP `500 Internal Server Error` without exposing database internals or stack traces.

---

## 8. Database Integrity and Concurrency

- **Database Engine**: MongoDB (compatible with both standalone local instances and MongoDB Atlas).
- **Replica-Set Independence**: Atomic concurrency and overdraft prevention rely on MongoDB's atomic conditional updates (`$inc` coupled with query filter `{ balance: { $gte: amount } }`). This ensures thread-safety under concurrent debit requests without requiring a replica set.
- **Index Optimization**:
  - Compound unique index: `{ accountId: 1, referenceId: 1 }` for idempotency.
  - History query index: `{ accountId: 1, createdAt: -1 }` for high-performance sorting and pagination.
